Across the five portfolios I used one case study, NexaCart, and kept each piece of work tied to the same data. The main lesson is that a database result only counts once it has been checked in a way that could have failed. Every portfolio therefore has a repeatable script or runner that checks its own outcomes and fails on a mismatch, and Portfolios 2 to 5 also use a hash of the original `public` data to show that the experiments left it unchanged or that a replica holds an identical copy.

**Design (Portfolio 1).** Separating `order_items` from `products` keeps historical sale prices independent of catalogue changes, and storing each payment as its own row keeps a failed attempt alongside the successful retry. Validation taught me the difference between a business rule and a constraint: a unique foreign key stops a second inventory row but cannot require the first to exist. Negative tests also have to check the specific error rather than accept any rejection, which is why a missing price check was deliberately tested in a disposable database and made the suite fail as it should.

**Optimisation (Portfolio 2).** The two targeted indexes cut customer history from 7.931 ms to 0.140 ms and daily fulfilled sales from 17.119 ms to 0.159 ms, but the all-order status summary stayed at about 41 ms, because an index does not help a query that needs every row. My hypothesis that the history index would remove the sort was also wrong: PostgreSQL chose a bitmap scan and the sort remained. Reading the plan was what showed this, so I report it rather than the cleaner story. These are local, warm-cache numbers and I do not present them as production results.

**Transactions (Portfolio 3).** Commit and rollback made atomicity concrete, since a stock decrement and its audit row either both persist or neither does. The most useful result was that a single guarded `UPDATE ... WHERE available_quantity >= 1` prevents an oversell, because the second session waits on the row lock and then finds no stock. It does not solve payment idempotency or retries, and I say so.

**NoSQL (Portfolio 4).** MongoDB suits NexaCart's read-oriented catalogue and profile views, where product attributes differ by category, but not the order workflow, so PostgreSQL stays authoritative and the document data is a deliberate copy. Checking the Mongo data against PostgreSQL exposed a wishlist entry that pointed to a product with no catalogue document. I fixed it and added a validation check. With only seven documents, `explain()` shows that the index is chosen and fewer documents are examined, not that the query is faster.

**Distributed systems (Portfolio 5).** Replication needed a rule in `pg_hba.conf`, because the default rules never match replication connections from another container. The recorded run showed the trade-off directly: an asynchronous replica returned a stale read and then converged, while a synchronous commit waited at `SyncRep` until the replica came back. Failover also stayed manual and left the old primary stopped to avoid split-brain, which showed how much a managed cloud service takes over.

**What I would do next.** I would test larger and skewed data, concurrent writes and a real multi-host network, and add automatic failover. I would also treat sharding the order tables as a design problem of its own, since a multi-product order would cross shards and lose the single-node locking that Portfolio 3 relies on.
